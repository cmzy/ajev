# AJev lora2 技术报告

> Gemma 4 12B + LoRA 的带类型决策模型 · 2026-10-02 · 适配器 `runs/gemma_lora2/best`（第 1,415 步，已校准）

## 摘要

AJev 是一个仿照 Jev 的**带类型决策模型**：输入一段材料（state）和若干问题，每个问题是 是/否（noul）、单选（choice）或打分（score），
输出每个选项的**校准概率**。lora2 是在 `google/gemma-4-12B-it` 上做 LoRA 微调的第二个正式版本。

在四个测试集上（材料上限都是 16K token，三个模型条件完全相同）：

| 测试集 | 题数 | 零样本 Gemma | lora1b | **lora2** |
|---|---:|---:|---:|---:|
| typed-decisions（业务决策） | 2,000 | 0.696 | 0.784 | **0.787** |
| JevBench public | 231 | 0.848 | **0.857** | **0.857** |
| Kev transfer v9 | 1,264 | 0.745 | 0.764 | **0.773** |
| eikos-decisions heldout | 1,190 | 0.928 | 0.929 | **0.937** |

- **业务题提升最大**：typed-decisions 比零样本高 9.1 个百分点，是我们所知同一测试集上公开成绩最高的（Verdict 2.0 为 0.771，Jev 为 0.727–0.738）。
- **概率更可信**：JevBench 的 ECE 从 0.112 降到 0.047，Kev v9 从 0.204 降到 0.057；打乱选项顺序后答案改变的比例在四个测试集上都下降了。
- **主要弱点**：JevBench 的难题（hard 档 0.712）和长材料题（材料超过 1,500 token 的 37 道题，0.676）不如零样本（0.730 / 0.784），也明显落后于 JevK5（hard 0.784）。
- 部署：提供 MacBook（Apple 芯片）一键部署包，内置 Playground 网页。在 GPU 上验证，部署包的推理结果与正式评测一致（231 道题中最可能选项一致率 99.1%）。

## 1. 任务定义

请求和响应格式与 Jev 兼容：

```json
{"state": "订单号 88231，耳机一周了还没发货，再不发货我就投诉！",
 "questions": {
   "category": {"type": "choice", "instructions": "这是什么问题？", "criteria": {"delivery": "物流", "refund": "退款"}},
   "urgent":   {"type": "noul",   "instructions": "需要马上人工处理。"},
   "anger":    {"type": "score",  "instructions": "客户有多生气？", "criteria": ["平静", "不满", "很生气"]}}}
```

| 题型 | 输出 | 说明 |
|---|---|---|
| noul | `{"noul": P(成立)}` | instructions 写成陈述句 |
| choice | 最可能的选项、各选项概率、置信度 | 2–26 个选项（大模型路线用字母 A–Z 表示选项） |
| score | 期望等级、各等级概率、置信度 | 2–10 个有序等级 |

置信度 = 1 − H(p) / ln K，其中 H 是熵、K 是选项数。1 表示非常确定，0 表示完全拿不准。

## 2. 技术方案

### 2.1 两条路线

| | 路线一：mmBERT 编码器（sft4） | 路线二：Gemma 12B + LoRA（lora2） |
|---|---|---|
| 基座 | `jhu-clsp/mmBERT-base`（3 亿参数） | `google/gemma-4-12B-it`（120 亿参数） |
| 打分方式 | 每个选项前放一个 `<mask>` 标记，由决策头给每个标记打分 | 选项写成字母 A、B、C……，只读模型“下一个 token 是哪个字母”的 logits |
| 训练 | 全参数微调，约 20 万道题 | LoRA，3.37 万道题，1 个 epoch |
| 速度 | 单题约十几毫秒 | 单题 54–137 ms（RTX PRO 6000） |
| 外部评测 | 弱（JevBench 0.584） | 强（JevBench 0.857） |

两条路线共用数据格式、损失函数和评测代码。小模型能学会业务格式（typed-decisions 0.775），但缺乏推理能力，在外部评测上落后 20–47 个百分点，所以正式版本选择了路线二。

### 2.2 大模型路线的打分方式

```
You are a decision model. Read the state and answer the question by picking exactly one option.

### State
{材料，超过上限按 token 截断}

### Question
{instructions}
{题型提示}

### Options
A. delivery: 物流
B. refund: 退款

Reply with the letter of the best option only.
```

- 只做**一次前向**，只取最后一个位置的 logits（`logits_to_keep=1`），从 26 万的词表里取出字母对应的 token。
  “A”和“ A”两种写法用 logsumexp 合并，然后在 K 个字母之间做 softmax。不生成任何文字。
- **材料放在最前面**：同一份材料上的多个问题共享相同的前缀，推理框架可以复用这段的 KV cache。
- 一批题采用左侧补齐，所有序列的最后一个位置都对齐在末尾。

### 2.3 训练数据（`data/lm1/train.jsonl`，33,700 道题）

| 类别 | 题数 | 内容 |
|---|---:|---|
| 中文公开数据 | 10,400 | AFQMC、CMNLI、OCNLI、TNEWS、MASSIVE 中文、ToxiCN、COLD、UltraFeedback 中文，各 1,300 |
| bev-decision | 9,000 | Jev 格式的多领域决策题：default / hard / skills / counterfactual / numeric |
| typed-decisions | 5,400 | 业务决策：发票、安全事件、客服、Agent 轨迹（来自其训练集，与测试集不重叠） |
| 业务 / Agent | 5,100 | 客服工单、When2Call、PKU-SafeRLHF、HelpSteer3、Feedback-Collection |
| 其他公开数据 | 3,800 | NLI、意图、情感等英文数据集，每个 200 道，主要用来学格式 |

共 41 个数据源。题型分布：choice 13,678、noul 12,328、score 7,694。中文 31%。
外部评测集与训练集已做重叠检查：按 40 字以上片段匹配，重叠为 0。

**为什么只用 3.37 万道，而不是全部 20 万道**：12B 模型每个 token 的训练成本约是 mmBERT 的 100 倍。
大模型本来就会读题和推理，LoRA 主要教它题型格式、业务约定和合理的概率；模板化的公开数据练得太多，反而会削弱推理能力。

### 2.4 损失函数

每道题的损失 = 软标签交叉熵 + 0.5 × RPS（只用于打分题） + 0.5 × 选项打乱一致性。

- **软标签交叉熵**：target 是概率分布，可以是 one-hot，也可以是多人投票的分布（如 HelpSteer3）。再加 0.05 的标签平滑。
- **RPS（排序概率得分）**：打分题的等级有顺序。“差一档”应该比“差三档”罚得轻，RPS 比较的是累积分布。
- **一致性**：是/否题和选择题的选项顺序随机打乱两次（视图 A、B），把两次的预测放回原始顺序后计算对称 KL，让模型不受选项顺序影响。
- **每道题权重相同**：先求和，再除以这一步的题数。每道题只有一个预测位置，所以材料长短不影响权重。

### 2.5 训练配置

| 项目 | lora2 |
|---|---|
| LoRA | r = 32，α = 64，dropout 0.05；作用于语言模型的 q/k/v/o/gate/up/down 投影；可训练参数 1.31 亿（1.08%） |
| 优化器 | AdamW，峰值学习率 3e-5，3% 预热后余弦衰减，梯度裁剪到 1.0 |
| 分批 | 按 token 预算分批（每批 12,288 token，最多 32 道题），开启梯度检查点 |
| 材料上限 | 16,384 token，超长的剔除（实际 0 道被剔除） |
| 尖峰保护 | 裁剪前梯度范数大于 100 时跳过这一步（共跳过 72 步，占 5.1%） |
| 规模 | 1 个 epoch，1,415 步 |
| 硬件 | Colab G4（RTX PRO 6000 Blackwell，96 GB），约 3.4 小时，约 31 个计算单元 |
| 校准 | 每种题型拟合一个温度：noul 0.962、choice 0.796、score 0.861。拟合数据为 1,500 道验证题和 600 道业务验证题；在留出的 630 道题上 ECE 从 0.069 降到 0.054 |

### 2.6 迭代中解决的关键问题

| 问题 | 现象 | 处理 |
|---|---|---|
| 学习率过大 | lr 1e-4 时 gnorm 达 204–313，loss 卡在 1.2–1.5 | 从第 200 步的 checkpoint 改用 3e-5 继续训练，并加上尖峰保护 |
| 推理截断 | 推理沿用训练时的 1,500 截断，JevBench 长材料题只有 0.35，被误判为“LoRA 损害推理” | 推理上限与训练上限分开设置，现在都是 16K |
| 训练截断 | 1,500 截断让 2.1% 的题看不到答案依据 | 改为 16K 上限，超长的题剔除而不是截断 |
| 依赖版本 | transformers 4.56 和 5.x 下 Gemma 4 的结果一致率只有 88% | 固定 transformers 5.17.0 |
| 数据切分 | When2Call 按顺序切分，评测集 100% 是同一类 | 先打乱再切分 |
| 云盘同步 | Google Drive 异步同步丢失大文件 | checkpoint 留在 VM 本地，下载时做 sha256 校验 |

## 3. 评测结果

评测条件：四个测试集，三个模型，推理材料上限都是 16,384 token。在同一张 RTX PRO 6000 上用 bf16 运行，LoRA 未合并。
lora1b 和 lora2 使用各自的校准温度，零样本模型不做校准。

### 3.1 准确率与概率质量

| 测试集 | 模型 | 准确率 | Brier ↓ | ECE ↓ | 翻转率 ↓ |
|---|---|---:|---:|---:|---:|
| typed-decisions | 零样本 | 0.696 | 0.115 | 0.280 | 6.4% |
| | lora1b | 0.784 | 0.015 | **0.147** | 5.8% |
| | **lora2** | **0.787** | **0.014** | 0.149 | **4.4%** |
| JevBench | 零样本 | 0.848 | 0.079 | 0.112 | 7.5% |
| | lora1b | **0.857** | 0.066 | 0.054 | **2.8%** |
| | **lora2** | **0.857** | **0.060** | **0.047** | 5.2% |
| Kev v9 | 零样本 | 0.745 | 0.125 | 0.204 | 12.7% |
| | lora1b | 0.764 | **0.088** | **0.044** | 10.0% |
| | **lora2** | **0.773** | **0.088** | 0.057 | **9.7%** |
| eikos | 零样本 | 0.928 | 0.035 | 0.053 | 4.0% |
| | lora1b | 0.929 | 0.023 | 0.052 | 2.5% |
| | **lora2** | **0.937** | **0.021** | **0.038** | **1.4%** |

翻转率是把选项顺序打乱后，最可能选项发生改变的题所占的比例。
typed-decisions 的标准答案是教师模型给出的软分布，所以这一行的 ECE 偏高，主要是指标本身的特点，原因见第 6 节。

### 3.2 按题型

| 测试集 | 模型 | choice | noul | score |
|---|---|---:|---:|---:|
| typed-decisions | 零样本 / lora1b / **lora2** | 0.668 / 0.730 / **0.730** | 0.798 / **0.858** / 0.853 | 0.640 / 0.767 / **0.779** |
| Kev v9 | 零样本 / lora1b / **lora2** | 0.703 / 0.729 / **0.746** | 0.830 / 0.843 / **0.848** | 0.719 / **0.725** / 0.706 |
| eikos | 零样本 / lora1b / **lora2** | 0.937 / 0.935 / **0.945** | 0.932 / 0.932 / **0.935** | 0.818 / 0.844 / **0.857** |

打分题的提升最明显：typed-decisions 上从 0.640 提高到 0.779。

### 3.3 难题与长材料

| 子集 | 题数 | 零样本 | lora1b | lora2 |
|---|---:|---:|---:|---:|
| JevBench easy | 48 | 1.000 | 1.000 | 1.000 |
| JevBench original | 72 | 0.931 | **0.986** | **0.986** |
| JevBench hard | 111 | **0.730** | 0.712 | 0.712 |
| JevBench 材料超过 1,500 token | 37 | **0.784** | 0.703 | 0.676 |
| eikos 材料超过 1,500 token | 106 | 0.887 | **0.934** | 0.925 |
| eikos 葡萄牙语 / 西班牙语 | — | 0.938 / 0.933 | 0.938 / 0.926 | **0.952 / 0.939** |

这是 lora2 的主要短板：训练时把材料上限放宽到 16K，JevBench 的长材料题和难题却没有改善。
可能的原因：

1. 训练集里的长题太少，而且大多是 bev_skills 这一种题型；
2. 长题容易组成只有 4–10 道题的小批次，梯度噪声大，尖峰保护跳过的 72 步大多是这类批次，所以长题实际学得更少；
3. JevBench hard 档考的是长政策、多步查找、日期和数字计算，训练数据里很少有这类题。

### 3.4 响应时间

在 RTX PRO 6000 上用 bf16 运行，HuggingFace transformers 实现，LoRA 未合并。单题延迟是逐道发送 50 道题测得的。

| 测试集 | 单题 p50 | 单题 p95 | 批量吞吐 |
|---|---:|---:|---:|
| Kev v9 | 64 ms | 74 ms | 28.9 题/秒 |
| typed-decisions | 78 ms | 91 ms | 17.7 题/秒 |
| JevBench | 73 ms | 493 ms（长文档） | 7.0 题/秒 |
| eikos | 137 ms | 314 ms | 6.0 题/秒 |

- 未合并的 LoRA 每层要多算一条支路，所以比零样本慢约 45%（typed-decisions 上 78 对 54 ms）。
  把 LoRA 合并进权重后，JevBench 上批量平均从每题 143 ms 降到 87 ms。部署包默认合并。
- 我们没有使用 llama.cpp、vLLM 这类推理框架，也没有用 CUDA graph 或前缀缓存，所以延迟还有很大的优化空间。

### 4.3 Kev transfer v9 与 eikos

- **Kev v9**：只有 Winnow 公开过成绩（Winnow 0.816，Jev 0.870，零样本 0.787），但用的是 1,046 道的“可判定”子集。
  我们评测的是全部 1,264 道（lora2 0.773），两者不能直接比较。
- **eikos heldout**：没有找到其他模型的公开成绩。imajev 的训练数据里有 10,570 条 eikos 数据，可能与测试集重叠。

### 4.4 解读

1. **同一个基座、同样的 LoRA 配置，lora2 和 Winnow-12B 的差别全在数据上**：
   JevBench 相同（0.857），typed-decisions 高 8.7 个百分点，ECE 更低。说明我们的训练数据在业务决策和校准方面更有效。
2. **难题上的差距来自训练数据，而不是模型大小**：
   4B 的 JevK5 在 hard 档比我们高 7 个百分点，它用了约 1.7 万道教师模型生成的难题。我们的训练数据以公开数据集为主，缺少多步推理类的难题。
3. **速度**：JevK5（H100，CUDA graph）单题约 13 ms，Winnow（llama.cpp Q8）约 22 ms，我们（HF transformers）64–137 ms。
   差距主要来自推理框架，而不是模型本身。

## 5. 部署

`deploy/mac/` 是 MacBook（Apple 芯片）一键部署工程，用 `deploy/mac/package.sh` 打包成 `dist/ajev-mac.tar.gz`（464 MB）。

```bash
tar xzf ajev-mac.tar.gz && cd ajev-mac
./install.sh    # Python 环境 + 依赖 + 下载基座模型（约 24 GB）
./run.sh        # 启动服务，浏览器自动打开 Playground
./verify.sh     # 与 GPU 上的正式评测结果对比
```

- 服务接口 `POST /v1/systemone` 与 Jev 兼容；`GET /` 是 Playground 网页，内置中英文示例：客服工单、发票审核、安全告警。
- **验证**：部署包在 Colab G4 上完整跑过一遍：安装、验证、启动服务。合并 LoRA 后，231 道 JevBench 题中最可能选项一致 225/227（99.1%，已排除几乎打平的题），概率平均绝对差 0.0064。
- **还没有在 M4 上实测**。12B 模型 bf16 约占 25–30 GB 内存，48 GB 的 M4 放得下。推理速度估计为每个问题 1–3 秒（1,000 token 左右的材料）。

## 6. 局限

- JevBench hard 档和长材料题弱于零样本，详见 3.3。
- typed-decisions 上的 ECE 有 0.149，看起来偏高，但这主要是指标本身的特点：这个测试集的标准答案几乎全是教师模型给出的软分布，
  标准答案里最大概率平均只有 0.659。lora2 给出的最大概率平均是 0.637，与之很接近。ECE 只看“最可能的选项是否正确”，
  模型输出与教师一致的分布时，按这种算法就会显得“不够自信”。按分布衡量的 Brier 只有 0.014，是四个模型中最好的。
- 尖峰保护的固定阈值误伤了 5.1% 的训练步，其中大多是长题批次。
- 部署包在 Apple 芯片上的速度和内存占用还没有实测。

## 7. 下一步

**lora3**（训练中）针对第 6 节的问题做了三项改动，数据和其他超参数不变，可以和 lora2 直接对比：

1. **每步固定 32 道题**：长短题按 512 道一块排序后组步，每道题的权重真正相同，长题不再组成小批次；
2. **尖峰保护改用相对阈值**：只有梯度范数超过最近 50 步中位数的 10 倍才跳过。lora3 训练前 8,000 道题时跳过 9 步，lora2 在同样多的题上约跳过 12 步；
3. **序数平滑**：只有一个评分者的打分题（Feedback-Collection、UltraFeedback 中文、HelpSteer2，共 2,300 道），one-hot 标签改为“正确等级 0.8，相邻等级平分 0.2”。

之后的方向：

- 补充多步推理、长政策、日期和数字计算类的难题，可以考虑用更大的模型生成，这是追上 JevK5 hard 档的关键；
